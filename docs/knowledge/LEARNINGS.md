# LEARNINGS.md

> Append-only. Newest first. Patterns that worked, pitfalls, workarounds.

## PITFALL-011: A root-relative URL from one container silently 404s when rendered by a different container's origin (2026-07-19)
- What happened: `UploadService.store()` (api) returns `/uploads/<category>/<uuid>.<ext>` — correct as a path on the `api` service, since that's exactly where `UploadResourceConfig`'s static handler serves it from. But every `<img src={...}>` that rendered an uploaded value (admin form preview, team card, project card, project detail) used that string verbatim. A root-relative URL in an `<img src>` always resolves against the *current page's* origin, not the origin that issued it — so from a page served by `web` (`http://localhost:3000`), the browser requested `http://localhost:3000/uploads/...`, which doesn't exist on that service at all, and the image silently 404s. `curl http://localhost:8080/uploads/...` (the api origin) always returns the file correctly, which is why API-level "does upload/re-serve work" checks never caught this — they were curling the right origin by construction. Nothing in the browser surfaces this as an application error either; it just renders as a broken image icon.
- Takeaway: a backend that returns a relative URL is implicitly telling the caller "resolve this against me" — that assumption breaks the moment a different origin (a separate frontend service, in this case) renders it directly without translation. Any URL crossing a service boundary into browser-rendered HTML needs either an absolute URL from the source of truth, or explicit resolution against the correct origin at the render site.
- How to apply: see `resolveUploadUrl()` in `web/src/lib/utils.ts` (feature 012 bug-fix pass 4) — prefixes `/uploads/`-prefixed paths with the browser-visible `NEXT_PUBLIC_API_BASE_URL`, leaves everything else (e.g. static bundled assets under `web/public`) untouched. Use it at every render site for a `photo`/`image`/`file` field that could hold an uploaded value.

## PITFALL-010: A public API client written for server-side fetches hangs forever when called from a client component (2026-07-17)
- What happened: `/admin/projects/new` and `/admin/projects/[id]` (both `"use client"` pages) called `getProjectFilters()` from `web/src/lib/api/projects.ts` directly inside a `useEffect`, to reuse the same sector/status/country vocabulary the public `/projects` page already fetches. That helper was written exclusively for server-side (SSR) fetches, where CORS never applies — same reasoning DEC-029 already documented for why the public read endpoints never needed a CORS policy ("`POST /api/leads` is called server-side ... never from the browser"). Called from an actual browser, the cross-origin GET (`localhost:3000` → `localhost:8080`) got no `Access-Control-Allow-Origin` header back (only `AdminSecurityConfig`'s chain, scoped to `/api/admin/**`, sets CORS at all), so the browser silently blocked the response and the `fetch()` promise rejected. Neither call site had a `.catch()`, so the rejection was unhandled and the `filters` state simply never got set — the page rendered "Loading…" forever with no visible error to the user, only a CORS message in the devtools console. Found by a human manually clicking through the admin console after QA had already approved the feature (testing.md v1.2) — QA's live verification exercised this CRUD path mostly via direct API calls, not by actually loading the edit/create UI in a browser, which is exactly the gap a real click-through catches that automated API-level checks don't.
- Takeaway: an API client function with no credentials/CORS story baked in (built for `next: { revalidate }` SSR fetches) is not safe to call from a `"use client"` component just because the URL is reachable — the browser enforces CORS on ANY cross-origin fetch regardless of whether the server would have answered fine to curl. If a client component needs public data, either fetch it server-side (a Server Component parent passing props down — the fix applied here, mirroring `(marketing)/projects/page.tsx`'s existing pattern) or add it to the CORS-enabled `/api/admin/**` surface. Don't assume a working `curl`/server-side fetch means a browser `fetch()` from a different origin will work too.
- How to apply: see `web/src/app/admin/(protected)/projects/new/page.tsx` and `.../projects/[id]/page.tsx` (now Server Components, `force-dynamic` for the same build-time-API-unavailable reason as `(marketing)/projects/page.tsx`) plus the new `edit-project-client.tsx`. When adding a new admin form that needs public vocabulary/reference data, fetch it in the page's Server Component, not in a client `useEffect`.

## PITFALL-009: A web-only `@Configuration` (Spring Security's `MvcRequestMatcher`) crashes a non-web profile's context (2026-07-17)
- What happened: `AdminSecurityConfig` (`@EnableWebSecurity`, string-path `.requestMatchers(...)`/`.securityMatcher(...)`) has no profile or `@ConditionalOnWebApplication` guard, so component scan loads it inside the `worker` profile's context too, even though `application.yml` sets `main.web-application-type: none` for `worker`. Because `spring-webmvc` is on the classpath (same fat jar as `api`), Spring Security resolves those string paths to `MvcRequestMatcher`, which requires a `HandlerMappingIntrospector` bean — one that is only registered when Spring MVC's actual web infrastructure is configured, which never happens under `web-application-type: none`. Bean creation throws and the whole context — and the container — fails to start. No test in the suite boots the context with `spring.profiles.active=worker`, so this went unnoticed through two QA passes until a pass that actually started every `docker compose` service, including `worker`.
- Takeaway: a `@Configuration` written for the web app is not automatically inert in a sibling non-web profile that shares the same codebase/jar — Spring only skips it if you tell it to. When a repo runs the same code under multiple `web-application-type`s (or multiple profiles with different infra), any config using web-only matcher types needs an explicit guard.
- How to apply: guard `AdminSecurityConfig` (and any future `/api/admin/**`-only config) with `@Profile("!worker")` or `@ConditionalOnWebApplication(type = Type.SERVLET)` before the `worker` process needs to actually run (see DEC-032, deferred since no consumer exists yet). Add a `@SpringBootTest(webEnvironment = WebEnvironment.NONE)` test with `spring.profiles.active=worker` as the regression check — it would have caught this immediately.

## LEARNING-003: An un-scoped SecurityFilterChain bean governs the whole app, not just the paths a feature intended (2026-07-15)
- What happened: Feature 012's `AdminSecurityConfig` defined `authorizeHttpRequests` rules that correctly `.permitAll()`'d everything outside `/api/admin/**`, and this was mistaken for "the rest of the app is untouched." It wasn't: with no `.securityMatcher(...)` on the `HttpSecurity` builder, and this being the *only* registered `SecurityFilterChain` bean, Spring Security routed every single request in the application through this chain — including its CSRF filter, which runs *before* the authorization rules and is not governed by them at all. The result: the pre-existing public `POST /api/leads` (feature 011) started returning a CSRF-shaped 403 for every real submission, invisible to `mvn test` because (a) `LeadControllerTest` correctly runs with `addFilters=false` (PITFALL-008) so never exercises the real chain, and (b) the one test that *did* exercise the real chain against a public endpoint (`AdminSecurityWebTest`'s "public endpoints stay open" check) only drove a `GET`, and CSRF never touches safe methods regardless of scoping.
- Takeaway: `authorizeHttpRequests` and CSRF enforcement are two *separate* filters in the same chain — permitAll-ing a path in one does not exempt it from the other. If a `SecurityFilterChain` is meant to own a subset of the app's URL space, say so explicitly with `.securityMatcher(...)`; don't rely on `.anyRequest().permitAll()` to "close the loop," because it only closes the authorization half. And when regression-testing "does a public endpoint still work," test at least one *mutating* (unsafe-method) request through the real chain, not just a GET — a GET can never reveal a CSRF-scoping bug.
- How to apply: see `com.alef.api.admin.security.AdminSecurityConfig`'s `adminSecurityFilterChain()` (DEC-029) and the regression test `AdminSecurityWebTest.public_lead_submission_endpoint_stays_open_without_authentication_or_csrf`.

## LEARNING-002: Spring Security 6 CSRF cookies are only issued on requests that actually require protection (2026-07-13)
- What happened: Building the admin CSRF flow (feature 012), two things were less obvious than expected. First, Spring Security 6's default CSRF request handler (`XorCsrfTokenRequestAttributeHandler`) defers token resolution until something reads the `CsrfToken` request attribute -- for a pure JSON API with no server-rendered view, nothing ever does, so the `XSRF-TOKEN` cookie is never written even though CSRF is "on." Switching to the plain `CsrfTokenRequestAttributeHandler` fixes eager resolution, but a second gotcha remained: `CsrfFilter` only calls the request handler at all on requests that match `requireCsrfProtectionMatcher` -- i.e. an unsafe method (POST/PUT/DELETE) on a non-ignored path. A plain `GET` never triggers cookie issuance, confirmed empirically while writing `AdminSecurityWebTest` (a `GET` to a protected or public endpoint came back with zero `Set-Cookie` header every time).
- Takeaway: for a cookie-based CSRF setup serving a JSON/SPA client (not server-rendered forms), you need (a) `CsrfTokenRequestAttributeHandler` instead of the BREACH-protected default, and (b) a dedicated priming endpoint the client calls once to force issuance, since no naturally-occurring request does it for you. Spring Security's own docs show the pattern: inject `CsrfToken` as a controller parameter and explicitly call `.getToken()` on it (merely accepting the parameter is not enough -- it's a lazy `SupplierCsrfToken` wrapper).
- How to apply: see `com.alef.api.admin.security.CsrfTokenController` (`GET /api/admin/csrf`, DEC-028) and `AdminSecurityConfig`'s class-level doc comment. The admin web client calls this once (e.g. on the login page mount) before its first mutating request.

## PITFALL-008: adding spring-boot-starter-security auto-secures every existing @WebMvcTest slice (2026-07-13)
- What happened: Adding `spring-boot-starter-security` (feature 012) made every pre-existing `@WebMvcTest` in the repo (ProjectControllerTest, TrustControllerTest, TeamControllerTest, OfficeControllerTest, LeadControllerTest) start returning 401/403 instead of their expected status codes. Spring Boot's test slice auto-configuration detects Security on the classpath and applies a default "secure everything" filter chain unless a `SecurityFilterChain` bean is present in that test's context or filters are explicitly disabled.
- Takeaway: any `@WebMvcTest` that predates a Security dependency addition and is not testing auth needs `@AutoConfigureMockMvc(addFilters = false)` added, or it silently breaks. This is a one-time, repo-wide fixed cost when Security is introduced, not a per-feature concern going forward (new endpoints outside `/api/admin/**` inherit "stays public" for free).
- How to apply: `@WebMvcTest(...)` + `@AutoConfigureMockMvc(addFilters = false)` on any slice test that isolates business/HTTP-contract logic rather than auth. Reserve a real (filters-enabled) `@WebMvcTest` + `@Import(AdminSecurityConfig.class)` for the dedicated auth test class (see AdminSecurityWebTest).

## PITFALL-007: ISR requires API at build time; force-dynamic is correct for Docker Compose (2026-06-24)
- What happened: Architecture spec prescribed ISR (revalidate=60) for the portfolio pages. In the Docker Compose setup, the web image is built before the api container starts, so any build-time API fetch (ISR initial render or generateStaticParams) fails and breaks the Docker build.
- Takeaway: force-dynamic is the correct rendering strategy when the API is not available at build time. Document the deviation rather than fighting the build order.
- How to apply: Keep `export const dynamic = "force-dynamic"` on both portfolio pages. Switch to ISR only if the deployment model guarantees API availability at build time.

## PITFALL-006: Spring AI Ollama auto-configuration starts eagerly (2026-06-22)
- What happened: Including the spring-ai-ollama-spring-boot-starter dependency causes auto-configuration to attempt Ollama connection on startup, even when no AI feature is active. Tests need explicit exclusion of OllamaAutoConfiguration.
- Takeaway: Exclude Spring AI auto-configuration in test profiles when the AI stack is not under test.
- How to apply: application-test.yml uses spring.autoconfigure.exclude to disable OllamaAutoConfiguration.

## PITFALL-005: Local JDK version vs Docker JDK version mismatch (2026-06-22)
- What happened: The pom.xml targeted Java 21 but the local machine has JDK 17. Compilation failed locally even though the Docker build (JDK 21) would succeed.
- Takeaway: Set the Maven java.version to match the local JDK for local dev. The Dockerfile's JDK version is independent. Document the requirement.
- How to apply: pom.xml uses java.version=17 for local compat; Dockerfile uses eclipse-temurin:21.

## PITFALL-004: Free LLM tiers may train on your data, and billing can delete the free tier (2026-06-18)
- What happened: Gemini's free tier is generous but free-tier inputs may be used for training, and enabling billing on a project removes the free tier for that whole project.
- Takeaway: Never send confidential uploads through a free tier. Keep prototype and production in separate projects.
- How to apply: Route only non-sensitive Q&A through a free tier; gate uploads to a paid/private model.

## PITFALL-003: JVM services are tight on tiny free hosts (2026-06-18)
- What happened: Free deploy tiers (e.g. Render free at 512MB) are cramped for a Spring Boot service, with cold starts on top.
- Takeaway: Budget ~$5/mo for an always-warm service, or build a GraalVM native image for low memory and fast startup.

## PITFALL-002: "Free" deploy tiers shift; verify before relying (2026-06-18)
- What happened: Fly.io removed its free tier (now a 2-hour trial); Railway has no permanent free tier ($5/mo); Vercel Hobby bans commercial use.
- Takeaway: Cloudflare Pages (free, commercial OK, unlimited bandwidth) and Render free (with cold starts) are the genuinely-free rungs. Re-check at deploy time.
